# ADR-0016: Independent encrypted credential packages

- Status: Accepted
- Date: 2026-09-30

## Format and encryption

Use a separate binary format with magic `CSHCPK01`, version 1 and a 56-byte header: magic (8), big-endian version (4), random salt (16), big-endian Argon2 memory/passes/lanes (12), random nonce (12), and big-endian ciphertext length (4). Encrypt the entire payload with AES-256-GCM, authenticating the complete header as AAD. Derive 64 bytes with Argon2id v19, 64 MiB, 3 passes, 4 lanes; use the first 32 bytes as the package encryption key. Each export uses a new salt and 96-bit nonce. Parameters follow the second recommended profile in [RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html#section-4); reuse the Vault's explicitly zeroized Argon2 working memory. This is an independent transfer password, not a Vault root key or a copy of the active Vault file.

The payload contains a length-prefixed encrypted context, record count, and records with UUID (16), kind (1), length-prefixed binding and secret. The context is strict JSON version 1 with saved Profile names, folder-name paths and complete SSH target records for selected Profiles and their jump dependencies. Credentials, target metadata, bindings and the complete record set are authenticated together. Kind 1 is a password, 2 a key passphrase, 3 an imported private key. Profile storage mode/root keys/master passwords/host-key trust/clipboard policies are not transferable records. Reject kind 4 and unknown kinds.

Limits: file 1 MiB, context 256 KiB, 128 credential records, 32 selected credential Profiles, 64 context targets, 32 folder levels; bindings and passwords/passphrases 4096 bytes, keys 64 KiB. New package passwords are 8–1024 bytes; unlock inputs are 1–1024 bytes. Reject incompatible KDF parameters, lengths, version and trailing bytes before deriving. Authenticate the entire package before interpreting context, kinds, UUIDs or secret bytes. Duplicate records and empty secrets are invalid. Errors and Debug do not expose peer metadata, tokens, ciphertext or secrets.

## Export and restoration

Export requires explicit saved SSH Profile selection and the saved catalog revision, Vault revision and lock generation. Read the selected active credential backend with its existing target/path binding. Missing credentials are omitted; access/binding/backend failures abort export. Agent secrets are not exported. Private key contents require an explicit checkbox and come only from previously imported encrypted Vault records; never read an external key path during package export. Refuse an export with no transferable records. Derive outside the Vault commit/lock gate and reject the result if the generation changes before publication. The desktop writes ciphertext using its synced, no-overwrite publication helper and does not link to the Vault crate.

Import the public Profile JSON first. Restore only into an existing unlocked encrypted Vault, in either master-password or system-root mode. Prefer a saved source UUID; otherwise require exactly one saved SSH Profile with the same name and full folder-name path. Require a one-to-one target mapping. Compare all target fields, including authentication, key/certificate references, agent settings and the complete remapped jump graph. Missing/ambiguous/changed targets reject restoration. Bind each imported credential to its destination UUID and current target; validate private keys with their packaged passphrase before accepting them. No Profile creation or SQLite credential policy transaction is mixed with the encrypted file transaction.

Fail/Skip/Replace apply to each entire destination encrypted credential group, including its Vault-mode record. Fail blocks all writes when a group exists; Skip retains all its records and current mode; Replace removes omitted credential fields and writes the packaged fields plus Vault mode in one batch. New groups also select encrypted Vault. Existing native keychain records remain in the keychain and are not used by restored Profiles; they are outside the destination encrypted group's conflict policy. A package without a private key may require a separate key import before authentication. Whole-file capacity and write failures preserve the prior Vault; uncertain file replacement locks it and requires explicit reload/inspection.

## Preview, IPC and concurrency

IPC minor 20 adds CREDENTIAL_PACKAGE bit 24 and Vault operations ExportPackage 11, PreviewPackage 12, CommitPackage 13. Both Vault control and package capability are required. New request tags 8–12 carry ciphertext, group policy, selected UUIDs, key-content opt-in and preview token. Response tags 12/13 carry ciphertext or typed preview. Reject mixed operation fields. The GUI sees credential kinds and target summaries, never plaintext credentials.

Preview returns mapped targets, group actions and a random single-use 32-byte token. Cache only ciphertext, policy, three captured revisions/generation and a 2-minute lease: at most four live leases and two concurrent package derivations. The password and plaintext package are released after preview. Confirmation requires re-entering the package password, consumes the token before authentication or revision checks, and revalidates catalog/Vault/generation. Failed confirmation requires a new preview and is never automatically retried. File/policy/revision changes, window close and workbench focus loss clear GUI passwords and preview; routine Vault polling cannot restore a consumed preview.

Serialize catalog mutations with the final restore check/write. Argon2 and key validation run on blocking workers outside the Vault lock/commit gate. The final bounded Vault transaction acquires the commit gate, rechecks generation/revision, invalidates pending authentication and replaces the encrypted file once. Expiry acquires the same gate before state to avoid inverted lock order. Immediate lock remains available on an independent authenticated IPC connection; existing SSH sessions are retained.

Blocking workers own the derivation permit and the final catalog mutex guard, so cancellation of the awaiting IPC future does not release either protection while background work is still running. Windows replacement of an existing Vault may retry only the identical owned, synced ciphertext staging file for OS codes 5/32/33, with seven backoffs totaling 127 ms. Creation and other errors do not retry. The destination is never removed and permissions are never changed. Missing/inaccessible staging after a failed replacement is an uncertain write: lock and reload rather than retry. Persistent replacement denial preserves the previous file and reports failure. This handles transient replacement failures without replaying a credential import transaction.

## Verification scope

Production KDF tests cover fresh encryption, metadata secrecy, wrong passwords, authenticated header/ciphertext tampering, hostile bounds and Vault-format separation. SQLite tests cover public JSON name/UUID remapping with jump targets, no-write preview, single-use confirmation, group conflict policies, stale catalog/generation and whole-batch capacity failure. Framed IPC tests cover both capability checks and invalid mixed/oversized requests. A real SSH test exports an imported key, removes both the source file and destination key, restores the package, and authenticates again. Pointer tests cover explicit selection, captured revisions, key-content default exclusion and password clearing. Native platform CI, GPU/visual review, external servers and Windows power-loss persistence remain separate acceptance work.
